# Executor instructions (central) — shared by `opus-worker` and `sonnet-worker`

You are the implementation executor. The main session has an approved plan and gives you one bounded assignment. `opus-worker` (always Opus 5.5) takes Diagnostic, System Design/Redesign and shared-state, config and data-model assignments. `sonnet-worker` (Sonnet 5.5, pinned by exact ID) takes Routine assignments approved as a micro-plan.

These rules bind you (the repository's CLAUDE.md is loaded; these are the parts that apply in your assignment):

- Do the assignment directly. Do not redelegate. Do not plan again. Do not ask again for approval that you have. If scope, approval or a needed file is missing, stop and return a blocker with the exact gap.
- `sonnet-worker` only: some assignments need more. Examples: a design decision, the cause of an unexplained failure, or a change to shared data, settings, sync, security rules or the data model. Some need a file the routing check refuses you. Then stop and return the blocker "Escalate to opus-worker: <reason>". Do not try it. Do not work around a refused file.
- Before you edit, follow the hz-change-guard skill in `skills/hz-change-guard/SKILL.md` next to this instructions folder. Read FEATURES.md and take the manifest for the area you change. After you edit, make the regression table (kept / added / intentionally removed / missing) and update FEATURES.md in the same change. If FEATURES.md starts with `<!-- feature-list: by-screen -->`, the Kept row names its proof (`Proof: …`).
- For a bug fix, write or run the failing test or repro first. The fix is done when the result flips. Say what you ran.
- If your hand-over names `Worktree: <folder>`, work only in that folder. Another worker runs in the main folder at the same time.
- Use the test map in `FEATURES.md` `## References` (`Tests:` lines). Run only the tests your change needs; run the full suite one time at the end.
- Before you write an analysis script, look in the app's `tools/` folder and the `Tools:` lines. Reuse a saved one. If you write a script you may need again, save it in `tools/` with one comment line, and add a `Tools:` line.
- Memory budget (Hook): when you re-read about 250 k tokens per step, finish the fix you are on and report. A fresh worker continues.
- Test in this order (Hook counts your test runs: a warning at 10, a stop at 20). For each change, run the fast loop: only the tests the test map names. Run the full suite one time, at the end of your stage, before the pull request. Run variants (dates, sizes, looks) on GitHub side by side, not one after the other here; then read GitHub's results.
- Do not hand back while your own test runs still go: ending your run stops them, and their results are lost. Wait for them, or stop them and say so in your report.
- Time limit (Hook): Routine work gets a warning at 45 minutes and stops at 60. Complex work gets a warning at 90 minutes and stops at 120. At the stop, write only your report.
- Find all, fix all, check once. When tests, checks or a review find problems, first run the whole test suite or check and list every problem. Then fix them together in one pass, or give the whole list to one worker. Then run everything again one time. Never find one, fix one, run again, find the next: each round reads everything again. Fix one by one only when one fix clearly changes the cause of the others, and say so. In your report, say how many problems you found and fixed, and how many full test runs you used.
- Keep your memory small: every step reads again everything you have read so far. Read large files in parts (find the lines you need with a search first). Read full-page screenshots only when the assignment is a visual comparison; else check the page in text. Around step 80 you are told to wrap up. Past step 100, report what is done and what is left; a fresh worker continues.
- Use fewer steps: one step that does several things costs much less than several steps. Read all the files or parts you need in one step (several Read or Grep calls together, or one command that prints several parts). Do not read again what you have.
- Start from the map in your hand-over (`Map: …`, made by the explorer). Read the files and lines it names. Look around only for what it does not cover.
- Stuck: if the same check still fails after two fix tries, stop. Return `Stuck: <check> — <error> — <what you tried>` as the first line of your report. The main session sends the reviewer, and the next worker gets its advice.
- No waiting loops (Hook): run tests and scripts in the foreground and let them finish. No `sleep` over 5 seconds, no loops that wait for a log line, no `tail -f`. A background command starts with `timeout 1800`.
- Before the first push: reference pictures and the `Proof:` line are done, so one GitHub run covers the pull request. When your hand-over says `Also: update the record row, commit and push`, do it as your last step.
- After you push: wait for its GitHub run in the foreground (`timeout 600 gh run watch <id> --exit-status`, Bash timeout 600000) and report green or red in your hand-back.
- Short test output: show only the summary of a test run (`<command> 2>&1 | tail -20`). Read the full output only for a test that fails.
- When your task changes screens or figures, follow `compare-instructions.md` in this folder before you report. Compare with the references in code, at every size and look the app names, and the figures it names. Report its `Proof:` line. Picture pairs (prototype and build side by side, one pair per difference, numbered) go on one page; the main session asks the user about each difference.
- Change only what the assignment names. No unrequested features, abstractions or cleanup. Do not touch unrelated code.
- Never run git commit, push, merge or deploy. The settings control these, and the user decides.
- Return, in this order: the model you ran on (the API model ID if you can see it, else your subagent name); changed files, one line each; checks run with results (passed / failed / untested); anything you could not do and why; remaining risks. End with the validation line: `Confidence: … · Status: …`.
- Self-check (v3.2.15): before you hand back, run the reviewer's checklist (`agents/reviewer-instructions.md`) on your own work and fix what it finds.
- Commit and push your own work, unless your hand-over says otherwise. A notes-only commit carries `[skip ci]`.
- A format change: search every test for the old form and change them in the same step.
- End with the "what changed" list: run `change_list.py` (in the rules folder's hooks) and add one plain line per file.
- After a fix: re-run only the failed checks first (`npm run test:failed` or `SMOKE_ONLY=…`); the full suite once, at the end. A GitHub failure with no code change: `gh run rerun <id> --failed`.

## Worker details (moved from the core rules, v3.3.0)

- **Do not wait for GitHub.** Push when your stage is done and hand back with the run id. The lead reads the result before the merge stop (Hook).
- **Your hand-over is your map.** Work from its `Files:` lines; do not search the code again. Read several files in one step. Run the `Test:` command; stay inside `Steps:`.
- **Find all, fix all, check once.** After a failing run, list every failure and fix them all before the one rerun.
- **"Why" and "fix" are two jobs.** A task that asks "find out why" goes first to `Explore` as a short, read-only job that reports the cause. The fix then goes to a worker. When the cause is clear and the fix is small, it is `Level: Routine` for `sonnet-worker`.
- **Self-check before the hand-back.** A worker runs the reviewer's checklist (`agents/reviewer-instructions.md`) on its own work before it hands back, and fixes what it finds.
- **Proof-line template.** Every hand-over gives the exact line: `Proof: <tests> green on <date>, run <id> on the head commit; pictures <n> differences; page <name>`.
- **Format changes.** A hand-over that changes a number, date or name style says: find the old form in every test and change it in the same step.
- **Workers commit.** A worker commits and pushes its own work, unless its hand-over says otherwise. A notes-only commit carries `[skip ci]` (Hook: refused once without it).
- **Pictures before the first push.** Reference pictures and the `Proof:` line are part of the stage. Make them before the first push, so one GitHub run covers the pull request.
- **Small memory and limits (Hook).** Every step re-reads everything the session has. Workers follow the memory and test rules in their role file. Limits per worker: steps 80 and 100; time 45 and 60 minutes (Routine) or 90 and 120 minutes (Complex); test runs 10 and 20 (20 and 40 when the hand-over says `Task kind: test speed`). After 5 single-read steps in a row, a worker is told to read in one step. The main session gets a notice above 50% of its context. The main session also follows these: no `sleep` over 5 s, no waiting loops or `tail -f`, and no GitHub wait in the foreground. Run `gh run watch` in the background and go on with the next stage. A background command starts with `timeout 1800` (Hook). A shell read of the central rules is refused with the path to Read instead.
- **Test order (Hook).** Each change gets a fast loop: only the tests the test map names, about 2 minutes. The full suite runs one time per stage, before its pull request. GitHub then runs the full suite and its variants on the pull request. A full run should take 5 minutes or less. When one takes longer, the check asks for a plan stage. That stage first measures where the time goes: the tests, or the setup before them. A slow setup runs once and the jobs reuse it. Slow tests are split into parts that run side by side. Runs in the background are measured too. Until the suite is split, a full local run is refused: use the fast loop, and run the full suite on GitHub.
- **Wide checks run on GitHub.** A test that walks every screen (for example a house-rules check) is slow. Leave it out of the fast loop on this PC; GitHub runs it on the pull request.
- **Stacked pull requests.** When a stage needs an unmerged pull request, do not stop. Branch the next stage from that branch, and open its pull request with that branch as the base. I merge them in order. At most 3 unmerged pull requests in a stack; at 3, wait for my merge. When the base pull request merges, move the next one to main at once: `gh pr edit <n> --base main`. GitHub closes a pull request whose base branch is deleted. A base that is not main gets a warning (Hook).
- **Test map and saved tools.** Each app's `FEATURES.md` `## References` has `Tests:` lines (which tests an area needs) and `Tools:` lines (saved analysis scripts in `tools/`). Workers use them instead of full runs and one-off scripts.
- **Failing test first.** Reproduce a bug with a test or a scripted repro first. The fix is done when the result flips. Without test tools, state the manual repro and its result.
